# 8054. Исправления после испытания v39

Владелец подтвердил установку v39, открытие нового дерева и разделов, работу Wi-Fi, отображение реальных Bluetooth-пар и HDMI 1/2. В v39 владелец также воспроизвёл отсутствие Android TV, блокировку выбора при включении и одностороннее изменение автокоррекции. Эта проверка относится к v39. Изменения v40 имеют аппаратный статус `BUILT_UNTESTED`.

## Bluetooth

`NativePage.BLUETOOTH` теперь ведёт к `NativeBluetoothPage` внутри существующей `BluetoothSettingsActivity`. Старый `NativeSections.Bluetooth.populate` создавал список имён в одной строке, переход к тому же списку и второй маршрут добавления. На странице v40 размещены переключатель Bluetooth, категория «Сопряжённые устройства» и один исходный `add_accessory` внизу.

Exact-8054 `AccessoriesFragment.updateAccessories()` создаёт обычные AndroidX `Preference`: использует alias и тип устройства, читает `BluetoothDevice.isConnected()`, передаёт аргументы в `BluetoothAccessoryFragment.prepareArgs` и сохраняет ограничения администратора. Один проверяемый smali-вызов передаёт этому методу категорию Bluetooth вместо всего экрана, поэтому обновление и удаление устройств не затрагивают тумблер и кнопку добавления. Для обычного штатного `AccessoriesFragment` возвращается исходный экран. Сохраняются слушатели ACL и состояния адаптера. Обновление при изменении пары вызывает тот же штатный обработчик. AutoPair, boot receivers и службы связи не менялись.

Публичный `BluetoothAdapter.enable()` вызывается только по нажатию при 8054, системном приложении, `BLUETOOTH_CONNECT` и допустимой политике пользователя. Android 13 сохраняет исключение для системных приложений. Тумблер обновляется по getter и показанным переходным состояниям. Запрос выключения показывает предупреждение и оставляет адаптер включённым, пока физический способ восстановления управления не подтверждён. Проверить этот способ отдельно, без выключения Bluetooth в первом проходе. [Android BluetoothAdapter](https://developer.android.com/reference/android/bluetooth/BluetoothAdapter#enable())

## Источники и запуск

Порядок страницы: «Выбор источника» с Android TV, HDMI 1 и HDMI 2, «Источник при включении», HDMI-CEC, «Автопереключение HDMI», «Совместимость HDMI (EDID)». Отдельная группа «Состояние входов» убрана. Состояние остаётся в summary соответствующего входа, читается через `TvInputManager.getInputState`. Статус ожидания относится к TV Input, а не к установленному видеосигналу или состоянию питания HDMI-устройства.

`NativeSections.Sources.home` отбрасывал launcher по `FLAG_SYSTEM`. `HomeDestination.resolve` сверяет текущий ответ PackageManager с доступными обработчиками `ACTION_MAIN / CATEGORY_HOME` и повторяет проверку при клике. Явный выбор система делает через назначенный HOME либо через единственный подтверждённый вариант при отсутствии назначения. Android resolver, com.my.settings и само приложение настроек исключены. Конкретный пакет, флаги и причина отказа на экземпляре владельца требуют живого resolver-отчёта.

`PowerOnSourceSecondaryController.onAttach` использует `HOME` как default для отображения OEM. Его callbacks сохраняют HOME либо фактический TV Input ID из `getHdmiInputId`. В MOD `NativeBootDestination.choices` использует тот же проверяемый список HW6/HW7, что и «Выбор источника», без зависимости от флага аналогового входа. Выбор приложения остаётся частью того же свойства `persist.trd.source_id`. Пустое значение не даёт подтверждённого исходного состояния для возврата. UI показывает доступные варианты, различает пустое, неожиданное и недоступное значение и блокирует запись в этих случаях. При временном отказе сохраняется прежний перечень до успешного чтения. Открытый список проверяет снимок исходного значения и повторно проверяет доступность обоих назначений. После setter либо исключения UI перечитывает фактическое сохранённое значение. На проекторе снять точное исходное значение и сопоставить его с реальным ID входа и доступными приложениями. Холодный запуск проверять отдельно, без автоматической перезагрузки.

## HDMI-CEC и EDID

Основной CEC остаётся read-only. `SourceSubMenuController.lambda$initView$12` совмещает основной setter, OEM energy confirmation, изменение eARC и Auto Off. Без согласованного исходного состояния и восстановления всей связки одиночный setter недопустим. `OemCecAutoOff8054` сохраняет только независимый `setTvSendStandbyOnSleep` с предварительным чтением CEC и readback. Подпись объясняет отправку команды выключения совместимому устройству. Проверяется блокировка Auto Off при выключенном CEC.

`CompatibleApis.setHdmiCecAutoWakeupEnabled` вызывает `setTvWakeOnOneTouchPlay`. Это разрешение разбудить проектор командой HDMI-источника, поэтому оно не выведено под подписью об исходящем включении устройств. Рабочий setter исходящего включения и пользовательский режим CEC Remote Pass Through в нужном направлении не подтверждены, активных строк для них нет.

`OemHdmiEdidHook.installStatus` показывает «Совместимость HDMI (EDID)», сохранённый режим и причину ограничения. `tv_input_hdmi_edid_version` связан с `g_fusion_picture__hdmi_edid_version`. В OEM `getVideoInfoData(6,...)` индекс 6 выбирает тип запроса. Контракт изменения отдельных HW6/HW7, пересогласование и возврат требуют проверки. MOD не пишет EDID.

## Коррекция при перемещении

В `OemMoveKeystonePreference.install` v39 метод `canWrite` пропускал ON без симметричной проверки. Stock `KeystoneSettingsSecondaryController.setMoveAutoKeystone` сохраняет свойство движения и меняет три OEM-виджета. В прикреплённом OEM UI изменение виджетов может вызвать слушателей и изменить выравнивание, обход препятствий и вертикальную коррекцию. У MOD отделённые виджеты, поэтому полный OEM callback со связанными изменениями при активной зависимости воспроизводить небезопасно.

В v40 оба направления разрешаются только при явно прочитанных нулях всех трёх зависимостей. При активной, неизвестной или недоступной зависимости тумблер показывает сохранённое движение и недоступен для записи. Проверки выполняются при отображении, перед вызовом и после него. Изменение состояния в процессе отражается реальным readback. Автоматические сбросы, записи зависимых свойств и повторы отсутствуют. Mock регрессия проверяет OFF → ON → OFF, активную и неизвестную зависимость, внешний и частичный переход и отказ setter. У ранее включённого состояния при ненулевых зависимостях сохранение экрана read-only намеренное. Сначала зафиксировать свойства и геометрию. Любое использование полного OEM-редактора для восстановления согласовать отдельно: его вход при выключенном или неизвестном движении может обнулить три зависимых свойства.

## Первый безопасный проход после разрешения

Сверить хеш APK из Exact CI. До изменений снять локальный отчёт на Windows.

```powershell
$serial = '<согласованный serial>'
.\diagnose_8054_v40.ps1 -Serial $serial
```

Скрипт из артефакта читает путь, пакет и версию, HOME resolver и кандидатов, TV Input, сохранённый источник, EDID, CEC, Bluetooth, четыре свойства коррекции и последние сообщения приложения. Отчёт хранится локально и может содержать имена и адреса Bluetooth-устройств. Команды изменения состояния в скрипт не входят.

После отдельно разрешённой установки и сверки версии открыть настоящий корень.

```powershell
adb -s $serial shell am start -W -n com.android.tv.settings/.MainSettings
```

Проверить отсутствующие дубли, получение фокуса, возврат, выбранный HOME, список аксессуаров, статусы CEC/EDID и коррекции. В первом проходе Bluetooth не отключать, автокоррекцию и boot source не переключать, проектор не перезагружать. Следующий проход согласовать по конкретному состоянию из отчёта. [План проверки и возврата к STOCK](8054_HARDWARE_TEST_PLAN.md)
