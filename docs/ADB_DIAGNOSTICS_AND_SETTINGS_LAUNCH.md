# TvSettingsPlus / KuSettings — диагностика на проекторе (Termux + ADB)

**Цель:** без изменения системы определить, кто обрабатывает вызов обычных настроек, какие сервисы KuSettings/KuSourceRJ запущены, какие Intent-фильтры/компоненты есть на устройстве, и совпадает ли реальная конфигурация с оригинальной OTA 8052. Проверка актуальна для обеих ревизий, но различия 8054 требуют отдельной интерпретации.

## Запуск в Termux на телефоне

Телефон должен быть уже подключён через ADB к проектору (как для предыдущих отчётов). **Не запускать команды внутри самого проектора.**

Одна команда для отправки владельцу:

```bash
pkg install -y android-tools curl zip unzip && termux-setup-storage && curl -fL https://raw.githubusercontent.com/MAX-TAC/Projector-Soft/main/tools/collect_tvsettingsplus_adb_diagnostics.sh -o "$HOME/collect_tvsettingsplus_adb_diagnostics.sh" && bash "$HOME/collect_tvsettingsplus_adb_diagnostics.sh"
```

Если Termux ранее уже имеет разрешение на хранилище, `termux-setup-storage` его просто переиспользует. Для первоначальной проверки соединения: `adb devices` должен показать проектор в статусе `device`. При отсутствии связи требуется повторное подключение/спаривание ADB по ранее согласованной инструкции.

Во время выполнения скрипт предложит **самостоятельно открыть настройки на проекторе штатной кнопкой пульта**, оставить их на экране и нажать Enter на телефоне. Этот этап особенно важен для поиска фактического запускаемого пакета. Скрипт ничего не запускает автоматически.

Итог: архив `TvSettingsPlus_Diagnostic_YYYYMMDD_HHMMSS.zip` в Downloads телефона (или в домашней папке Termux, если доступа к Downloads нет). **Перед пересылкой желательно проверить архив на имена сетей, аппаратные идентификаторы и иные частные данные.**

Весь сбор — только чтение: `dumpsys`, `cmd package resolve-activity`, `query-activities`, `pm list/path`, `getprop` и чтение OEM конфигураций. Без root, `su`, `pm disable-user`, `pm clear`, `am start`, перепрошивки, установки APK, перезагрузки или остановки служб.

## Что именно выясним

1. Какой пакет сейчас выбран Android для `android.settings.SETTINGS` и восьми дополнительных OEM действий, сколько кандидатов доступно.
2. При обычном открытии меню с пульта: какая Activity реально находится на экране.
3. Доступность стандартного `TvSettingsPlus.MainSettings` через компонентное разрешение.
4. Включены ли `com.my.settings` и `com.android.provision`, какие сервисы/receivers экспортируются.
5. Существуют ли `KuSourceRJ.BootupReceiver`, `TimeService` и `KuSettings.MySetTimeService`, работают ли они во время снятия диагностического снимка.
6. Совпадают ли `settingApps` и `whaletv_config` на реальном устройстве с конфигурациями прошивки 8052.
7. Имеет ли устройство ревизию 8052 или 8054, чтобы выбрать совместимый APK. Одним снимком нельзя доказать надежность после аварийного завершения сервиса — это отдельный последующий тест с разрешения владельца.

## Важное: можно ли полностью отключить KuSettings?

Статический анализ 8052 подтверждает, что KuSetupWizard содержит собственный Java-код (14/15 DEX идентичны; оставшийся отличается одним `WarningActivity`). Подавляющее большинство OEM компонентов не имеет прямых строковых ссылок на пакет старых настроек. Но это НЕ эквивалентно доказательству отсутствия скрытых зависимостей.

На прошивке остаётся `settingApps: ["com.my.settings"]` и системный `services.jar` с обработкой `AUTO_BLUETOOTH`. В v2 есть 9 Intent aliases, но **старый KuSettings продолжает регистрировать такие же actions**. Android может предпочесть старый обработчик или запустить его через явный ComponentName. Подмена подписанного APK сама по себе приоритет или привязки не меняет.

После получения отчёта потребуется отдельно установить функциональную TvSettingsPlus MOD, подтвердить поведение пульта и OEM служб, затем только в контролируемом тесте отключать KuSettings. Удалять APK из /system не требуется.
