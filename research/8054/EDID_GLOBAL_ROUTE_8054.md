TvSettingsPlus.apk SHA-256 `f8e0c6fe0f46e7eb8db651c31d85ef8b32a769b37e4dd0f96ed19a64725d74ee`; TvServices.apk SHA-256 `2934ca9334afd0a2af85786aa0593d27da216086c7eb9b0c9b801f412516b77d`; MtkTvInput.apk SHA-256 `59040206f84c7fbd85f61f885cb5edbdd977ebea3a2a3b20a6b7afc138df72b2`.

В `TvSettingsPlus` два OEM getter: `EdidSourceSecondaryController#getEdidVersion` и `SourceSubMenuController#getEdidVersion` передают `0x6` в `MtkTvAVModeBase#getVideoInfoData` и читают `getU8EdidIndex`. Восемь radio `onClick` в secondary controller и fragment пишут значения 0..3 в один `Settings.Global.tv_input_hdmi_edid_version` через `SettingsUtil#putGlobalValueInt`. В этих обработчиках физический порт не передаётся.
2. `TvServices.TVMenuSettingsService#initMapdata()V`, `smali/com/mediatek/tv/agent/TVMenuSettingsService.smali:3051-3058`, кладёт в `itemIds` карту `"tv_input_hdmi_edid_version" → "g_fusion_picture__hdmi_edid_version"` с вызовом `Map#put`. В конструкторе этой службы строка присутствует в перечне настроек на строке 529. Это точное соответствие имён, а не ещё доказанный вызов `MtkTvConfig#setConfigValue` или иной HAL.
3. Read-only поиск точного литерала по распакованным smali дал: TvSettingsPlus 20 вхождений, Factory 1 (поле константы), KuSettings 0, MtkTvInput 0, TvServices 2. Отсутствие литерала в MtkTvInput не исключает вызова через Binder/конфигурационный ID или native слой.
4. `TVMenuSettingsService#syncConfigDataToSetting()V`, строки 4933-4971, передаёт весь `itemIds` в `updateSettingDB(Map)`. `updateConfigDataChanged(String)`, строки 5378-5627, делает то же для отдельных категорий изменений. `formatSettingToConfigId(String)`, строки 1179-1192, возвращает `itemIds.get(key)`; его callsite пока нужно найти.
5. `updateSettingDB(Map)`, строки 5755-5805, передаёт карту в `TVAsyncExecutor#execute` как `TVMenuSettingsService$2`. `$2#run()V`, строки 42-265, перебирает `Map.Entry`, читает `TVSettingConfig#getConfigValueInt(entry.value)` (строка 83), сравнивает с `getSettingStringValue(resolver, entry.key)` и при отличии вызывает `putSettingValueInt(resolver, entry.key, value)` (строки 165/196). Это направление **config → Settings**. `getSettingStringValue`, строка 6164, вызывает `Settings.Global#getString`; `putSettingValueInt`, строка 6707, вызывает `Settings.Global#putInt`. `access$600` также вызывается после записи; его назначение не установлено. Перегрузка `updateSettingDB(Map,int)` использует аналогичный `$3#run()V`.
6. Обратный путь: `TVMenuSettingsService#<clinit>`, строки 201-210, берёт `BASE_URI` из `Settings.Global.CONTENT_URI`. Конструктор кладёт EDID key в регистр `v124` (строка 529), `filled-new-array/range {v3 .. v161}` создаёт `prefKeys` (строки 606-610), а `access$100` возвращает `prefKeys` (строки 648-655). `$1#run`, строки 38-86, регистрирует `SettingObserver` для каждого элемента этого массива на URI из `buildUri(key)` (строки 1009-1028). `SettingObserver#onChange`, строки 52-205, снимает имя key из URI, вызывает `formatSettingToConfigId(key)` и для обычной ветки `updateConfigData(configId,key)`. `updateConfigData`, строки 4986-5376, читает значение Global через `getSettingStringValue`, сравнивает с конфигурацией и в общей ветке вызывает `TVSettingConfig#setConifg(configId,int)` на строке 5299. `TVSettingConfig#setConifg`, строки 472-508 в **TvServices.apk**, вызывает `MtkTvConfigBase#setConfigValue(configId,int)` на строке 503. Специальные ветки для видео/звука и условия раннего выхода видны в smali; для EDID динамическая достижимость общей ветки ещё не проверена. ## Подтверждение интерфейса STOCK 8054

- `EdidSourceSecondaryController.getEdidVersion` (129–153), `SourceSubMenuController.getEdidVersion` (300–344) и `EdidSourceFragment.getEdidVersion` (121–146) используют `getVideoInfoData(6, model)` → `getU8EdidIndex()`. `MtkTvAVModeBase` именует первый параметр `type` в журнале (639), передаёт его и model в JNI (654) и возвращает model. Числовой результат JNI в этой обёртке игнорируется. Проверенной связи `6` с HW6 или физическим индексом нет. Среди вызовов `getU8EdidIndex` в просмотренных APK отдельного обращения с HW7 не найдено.
- `SourceSubMenuController.updateEdidEnableState` (2245–2311) проверяет `PreferenceConfigUtils.isHDMISource`. Тот сравнивает `SaveValue.readWorldInputType` с 17 (3359–3365), где источник данных — `MAIN_INPUT_TYPE` (381–386). Это проверка типа HDMI без выбора HW6/HW7. `EdidSourceFragment.initData` берёт `mEdidSupportVersion` из OEM getter и отдельно читает Settings.Global, затем ограничивает отображаемый режим и сохраняет его в `curEdidVersion` (377–399). Значение getter используется как верхняя граница совместимости в UI. Оно не является показанием EDID, фактически выданного источнику.
- В обоих редакторах четыре radio ID связаны с записываемыми кодами: **0** → HDMI 1.4 (`rtv_source_edid_1_4`), **1** → HDMI 2.0 (`rtv_source_edid_2_0`), **2** → Авто (`rtv_source_edid_auto`), **3** → HDMI 2.1 (`rtv_source_edid_2_1`). Проверено по `initCheck`, обработчикам `$1–$4.onClick` и stock resource IDs 0x7f0a0384–0x7f0a0387. Обработчики сначала проверяют видимость варианта, затем пишут Global и меняют выбор в UI. Отдельная команда переподключения, HPD или восстановление транзакции в этих callbacks отсутствует. При открытии UI заново читает Global. Воссоздавать прошлое состояние можно только после определения адресата, повторно выбрав исходный режим штатным UI с разрешения владельца.
- Свежая трасса библиотеки MediaTek для PIC установила, что общий `MtkTvConfigBase.setConfigValue(String,int)` идёт в `TVNative.setConfigValue_native(-1, configId, value, 3)`. Это уточняет прежнюю границу расследования. Для EDID подтверждён один Java/config канал и отсутствие параметра порта в этой цепочке. Нельзя установить, использует ли native общий EDID для всех портов, активный вход или другой внутренний адресат. Hotplug, handshake и путь восстановления на каждом порту остаются аппаратными блокерами. [Stock EDID/CEC trace](https://github.com/MAX-TAC/Projector-Soft/actions/runs/44362169989/job/135006219140)

## Read-only проверка после разрешения владельца

Из корня репозитория на компьютере владельца запустить Python 3.10+ с точным разрешённым серийным номером и новым каталогом на каждый снимок. Пример для Linux:

```sh
python3 install-kit/preflight.py --hdmi-stock --serial "APPROVED_SERIAL" --out /tmp/stock8054-hdmi1-edid
```

Режим переиспользует барьеры STOCK preflight. После проверки 8054/API33/UID shell, пути и SHA-256 штатного APK он собирает `settings get global tv_input_hdmi_edid_version`, `dumpsys tv_input`, `dumpsys hdmi_control`, сведения о TvServices и build fingerprint. Выход `stock-hdmi.json` и сырые `.txt` сохраняются локально. `CAPTURED` подтверждает только валидный provider-код 0–3. `PARTIAL` означает отсутствующий, отклонённый или недопустимый код. `STOP` означает, что идентичность STOCK либо вывод на компьютере не подтверждены. Для `dumpsys` имеются собственные статусы `OBSERVED/DENIED/UNAVAILABLE`.

По отдельности наблюдать уже стабильные HDMI1 и HDMI2 с указанием физического источника и его режима. Снять Global и наличие/сессии TV Input для обоих. Дополнительно сверить EDID, который внешний источник действительно получает, по его штатному read-only интерфейсу или анализатору, если он уже доступен владельцу. Предпочтительно одно и то же внешнее устройство и согласованные условия сигнала. Глобальный код, состояние подключения и HDMI-CEC dumps по отдельности не идентифицируют применённый EDID. Уточнение области записи, требования к повторной синхронизации и возврата к исходной конфигурации потребует отдельного разрешения на управляемый тест STOCK. MOD показывает одну строку сохранённого режима и сохраняет 8054 EDID setter закрытым.
