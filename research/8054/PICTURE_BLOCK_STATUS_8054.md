# Изображение на 8054

`PICTURE_NATIVE_UI_READ_ONLY / BUILT_UNTESTED`. PIC01–PIC12 читаются в Android TV Settings через `OemPictureState.readStored` и `Settings.Global.getString`. Пустые и некорректные строки показываются как недоступные. При изменении mode/temperature/HDR между началом и концом чтения снимок отбрасывается. При подключении View, получении фокуса и уведомлении о ключе выполняется повторное чтение. В обычном дереве 8054 ссылки в китайскую панель изображения нет. Штатные Activity сохранены для совместимости.

## PIC03–PIC05. Маршрут TvServices

| ID | Ключ Settings.Global | Config ID в `initMapdata` |
|---|---|---|
| PIC03 | `picture_brightness` | `g_video__brightness`, smali 2352–2356 |
| PIC04 | `picture_contrast` | `g_video__contrast`, 2361–2365 |
| PIC05 | `picture_saturation` | `g_video__vid_sat`, 2370–2374 |

`TVMenuSettingsService$1.run()` регистрирует `SettingObserver` для `prefKeys`. Из уведомления `SettingObserver.onChange(Z, Uri)` извлекает имя ключа, берёт config ID через `formatSettingToConfigId` и на строках 171/176 передаёт пары config ID + ключ в `updateConfigData`, затем ключ в `updateConfigDataChanged`. `updateConfigData` читает текущий ACFG и заново читает Global (5033–5045), преобразует целое, сверяет его с буфером по config ID и может завершиться раньше (5121–5135). Для трёх ключей общая ветка вызывает `TVSettingConfig.setConifg(configId, int)` (5299), который возвращает результат `MtkTvConfigBase.setConfigValue(configId, int)` (503). Наблюдатель этот результат не подтверждает отправителю.

При смене `picture_mode` или `picture_color_temperature` `updateConfigDataChanged` вызывает `updateSettingDB` (5400–5427). Задача, которую отправляет `TVAsyncExecutor.execute` (5802), читает `getConfigValueInt(configId)` и при необходимости пишет значения обратно в Global (`TVMenuSettingsService$2.run`, 83–207). Поэтому значение сразу после записи может ещё отличаться от окончательного. Буфер, URI, команда и обратное чтение на этих участках не несут идентификатора профиля. [Исходная трасса TvServices](https://github.com/MAX-TAC/Projector-Soft/actions/runs/44123938819/job/134182455124)

## Stock PictureFragment. Точка входа, callback и JNI

1. `partnercustomizer.picture.PictureActivity.createSettingsFragment` передаёт имя `partnercustomizer.picture.PictureFragment` и `null` в `SettingsFragmentProvider.newSettingsFragment` (137–144). Hotkey mode/format создаёт другие фрагменты.
2. `PictureFragment.onCreatePreferences` получает `TVSettingConfig.getInstance(Context)` и `PreferenceConfigUtils.getInstance(Context)`, затем строит настройки через `createPreferences` (3393–3415). Эта инициализация отдельно вызывает `disableAutoBackLight` и `updateOLEDVisible`. MOD не вызывает жизненный цикл stock-фрагмента ради одного ползунка.
3. `createPreferences` читает набор `PartnerSettingsConfig.getSettingsList("picture_effects")` (192–195) и строит `ProgressDialogPreference` для brightness/contrast/saturation (370/415/460), передавая ключ и аргумент `PREFERENCE_ROOT`. Перед созданием contrast и saturation применяется `PreferenceConfigUtils.isVGASource(Context)` (404/449). `updateSomePrefEnabled` учитывает `picture_mode = 14` для saturation (3197–3228). В `isVGASource` проверяется `SaveValue.readWorldInputType(Context) == 16` (3545–3551); это тип сигнала для видимости. Это условия доступности. Доказательства, что в обработчик записи передаётся вход, нет.
4. `PictureFragment.onPreferenceChange` получает `Preference.getKey()` и направляет пять ползунков, включая PIC03–05, в `onPfChange(Preference, Object, String)` (3527–3576). OEM может показать подтверждение энергопотребления `isSupportPowerConfirmed/isNotFirstChange` (3583–3614). В `onPfChange` наличие `mStartKey` вызывает BACK (2003–2022), затем передаются только fragment, preference и новое значение в `updatePreferenceChanged` (2028); вызовы AIPQ находятся в отдельной ветке.
5. `PreferenceConfigUtils.onPreferenceValueChange` для `ProgressDialogPreference` извлекает int из String/Integer и использует его для summary (3939–3982). `updatePreferenceChanged` исключает sentinel -1000 и передаёт ContentResolver, `Preference.getKey()` и целое значение в `putSettingValueInt` (4612–4633). Тот вызывает `Settings.Global.putInt` (326) без передачи его результата вызывающему.
6. `PictureFragment.onResume` обновляет progress summary, Dolby Vision и доступность UI (3892–3898). В отдельном `ProgressBarVerticalFragment.onPreferenceChange` PIC03–05 тоже направляются через `updatePreferenceChanged` (1364), с возможной OEM веткой первого подтверждения. `onCreatePreferences` этого фрагмента передаёт ключ и config ID в `createNewProgressPreferencesss` (979–987). Китайские `PictureModeValueSecondaryController$1–3.onValueChanged` передают те же ключи и значение в `SettingsUtil.putGlobalValueInt`, который вызывает Global.putInt (103).
7. `TVSettingConfig.getConfigValueInt(configId)` вызывает `MtkTvConfigBase.getConfigValue(configId)` (160). Read получает `inputGroup = -1` через overload (536–539) и вызывает `TVNativeWrapper.getConfigValue_native(-1, configId)` (521). Write получает `inputGroup = -1`, `isUpdate = 3` (1025–1030), и вызывает `TVNativeWrapper.setConfigValue_native(-1, configId, value, 3)` (996). На устройстве wrapper передаёт те же аргументы в `TVNative` (6566/17968).

Программный маршрут STOCK выбирает адресата ниже UI и Java-кода TvServices, на границе MediaTek JNI. `-1` обозначает аргумент штатного вызова. Статически из этого Java-кода нельзя узнать, во что native его разрешает при начавшемся HDMI/PQ переключении, и какое значение сохранится в каждом профиле. Для MOD по-прежнему отсутствует подтверждение адресата и завершённого readback, достаточное для восстановления исходного значения. Production write/replay остаются закрыты. [Exact-8054 trace](https://github.com/MAX-TAC/Projector-Soft/actions/runs/44352714404/job/134972414645)

## Минимальная проверка контекста и восстановления

[Команды preflight, ручной тест STOCK и матрица допуска записи](STOCK_PICTURE_DIAGNOSTICS_8054.md).

1. С разрешения владельца снять на STOCK значения Global и OEM config для PIC03–05 в стабильных HDMI1/HDMI2 и двух доступных режимах. Зафиксировать источник главного окна, формат сигнала (SDR/HDR), режим и допустимый диапазон OEM. Взять снапшоты до и после каждого переключения до установившегося состояния. Различие значений между снимками показывает переключение или синхронизацию, но само по себе не доказывает отдельное долговременное хранение.
2. Отдельно согласовать ручную регулировку только PIC04 на STOCK. Изменить контраст на один шаг в HDMI1, дождаться согласования Global и OEM config, перейти на HDMI2 и обратно, затем повторить для смены режима. Сопоставить время `SettingObserver.onChange`, `TVSettingConfig.setConifg` и обратной синхронизации со сменой источника, если диагностические логи доступны. Отсутствие таких событий в логах не считать подтверждением.
3. На исходном HDMI и в исходном режиме вернуть значение штатным экраном. Сверить оба HDMI и исходный режим после повторного входа. Если write едет на новый профиль либо невозможно определить, какой профиль принял запрос, оставить MOD write/replay заблокированными. Для допуска нужен подтверждённый механизм адресации либо OEM-сигнал, позволяющий привязать baseline и подтверждение применения к тому же актуальному профилю при переключениях. Провайдерного readback для этого недостаточно.

PIC01/02 меняют несколько зависимых значений через асинхронную синхронизацию. Для PIC06/07 отдельно сверяются OEM bounds и шаг, у sharpness есть особая ветка диапазона. PIC08–10 связаны с `picture_color_temperature` и соседними компонентами. Для PIC11/12 требуются штатные условия HDR/MEMC, MEMC не равен MJC demo. Сброс затрагивает несколько OEM ключей и остаётся закрытым до подтверждения профиля и всей последовательности.

## Тесты

`OemPictureStateTest` покрывает повторную запись, отсутствие baseline, частичное восстановление, новое создание транзакции, смену режима/HDMI, отказ журнала и карантин UNKNOWN. `OemPictureAdapterTest` проверяет production fail-closed в JVM с Android fakes. `PicturePanelStateTest` проверяет пропуск отсутствующего и повреждённого значения, отбрасывание снимка при смене режима, чтение зависимых значений и продолжение регистрации после отказа одного ключа. Изолированный `OemPicturePanelAdapterTest` вызывает production bind для повторного attach, пересоздания, возврата, focus refresh и teardown с частичным отказом подписки. Реальный D-pad, fragment navigation и Android lifecycle требуют теста установленного APK.

Программный откат этой итерации выполняется отменой коммита исходников. Восстановление записей MOD при неизвестном профиле заблокировано.
