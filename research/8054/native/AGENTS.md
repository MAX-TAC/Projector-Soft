# Правила работы агента: MediaTek / TvSettingsPlus exact-8054

Эти инструкции распространяются на `research/8054/native/` и все вложенные каталоги. Не переопределяют глобальную политику безопасности проекта.

## Цель

Выполнить проверяемую, последовательную reverse-engineering трассировку пользовательских функций TvSettingsPlus MOD v41 на **оригинальной прошивке владельца exact-8054**, сопоставив UI → OEM Java/DEX → TvServices → JNI → native C/HIDL/RPC → аппаратный эффект (последний только в согласованном тесте). Повысить долю действительно функционирующих настроек, не подменяя OEM API догадками.

## До начала каждого исследования

1. Проверить текущую ветку / SHA, GitHub Draft PR #3, [README.md](README.md), [HANDOFF.md](HANDOFF.md), [INDEX.md](logs/INDEX.md), последний журнал, [TRACE_001](TRACE_001_PICTURE_CONTRAST.md) — [TRACE_003](TRACE_003_MEDIATEK_CONFIG_JNI.md) и результаты `generated/`.
2. Проверить актуальность исходников и не перепутать exact-8054 с 8052. Учитывать, что PR #2 — основная ветка разработки MOD v41; исследовательский PR #3 не должен менять её без отдельной задачи.
3. Зафиксировать входной SHA, исходные бинарные SHA-256, цель/гипотезу и риск в **новом журнале** `logs/YYYY-MM-DD_TASK-ID.md`, а не только в чате.

## Для каждого отдельного пункта

- Выделить STOCK UI screen/Preference key, обработчик, java/smali метод с сигнатурой и конкретным callsite.
- Найти MediaTek config ID (если есть), путь Global/SystemProperties/Intent/Binder/HIDL, единицы, min/max, значения enum и зависимости.
- В оригинальном `system/vendor/product/system_ext` найти native ELF SHA-256, экспорт/регистрацию JNI, relocation/xref, target C wrapper и HIDL dispatch; если извлечение невозможно, явно указать границу.
- Отдельно указать **все** побочные эффекты, асинхронность, контекст HDMI/SDR/HDR/PQ, выход звука, ограничения платы и восстановление.
- Не заменять MediaTek Factory-калибровочные API пользовательскими getter/setter без доказательства одинакового контракта.
- Сопоставить со способом реализации MOD v41 и составить точный diff логики: `STOCK route` vs `MOD route`.
- Записать отчёт `TRACE_00N_<FUNCTION>.md`, команды/версии инструмента, источники с URL, положительные и отрицательные свидетельства.
- Обновить индекс и журнал. Коммитить структурированные текстовые выводы и исходники исследовательских скриптов непосредственно в GitHub; сообщать commit SHA и URL PR.

## Схема доказательств

`STATIC_KEY_MAP` → `JAVA_SMALI_CALLSITE` → `EXACT_NATIVE_ELF_EXPORT` → `NATIVE_CALL_EDGE` → `HIDL_RPC_RECEIVER` → `READBACK_CONFIRMED` → `HARDWARE_EFFECT_VERIFIED`.

Присваивать **только достигнутый уровень**, не путать DT_NEEDED с непосредственным вызовом, экспортированный символ — с доступным API, readback — с изменением физического видеотракта/звука. Помечать `NOT_FOUND`, `UNKNOWN`, `INFERRED`, `NOT_TESTED` там, где этого требует доказательная база.

## Безопасность

- Дамп системы является источником для **read-only** анализа; проектор не подключён к этому чату автоматически. Без явного разрешения владельца не выполнять установки APK, запись Global/property, изменения системы, hardcoded JNI, root/I²C, EDID HPD, factory reset, calibration, PEQ save, fan/thermal/Watchdog, отключение критических служб.
- Не распространять бинарники и приватные данные из архива: публичному GitHub передавать только санированные текстовые выводы, названия ELF и хеши, точные имена функций, минимальные фрагменты собственных скриптов, без уникальных аппаратных идентификаторов, ключей и секретов.
- Для code review и экспериментов сохранять точную ревизию исходного APK; для v41 маркировать `BUILT_UNTESTED` вплоть до аппаратной проверки.
- Исследования делать по **одной функции за итерацию** и фиксировать завершение/блокер до перехода к следующей.
